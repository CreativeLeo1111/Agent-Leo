
# 第四章：工具


## 本章主线

工具让 Agent 能够获取外部信息、执行操作，并与其他 Agent 或人协作。设计工具时，需要回答两个不同的问题：**一项能力应该做成什么形式？**
**一次应该让模型看到多少项能力？**前者影响调用方式和单项能力的上下文成本，后者影响模型选工具的准确性和整体上下文开销。

## 4.1 工具的分类

| 工具类型 | 作用 | 例子 |
| --- | --- | --- |
| 感知工具 | 获取外部信息 | 搜索网页、读取文件、查询数据库 |
| 执行工具 | 改变外部世界 | 编辑文件、运行命令、发送邮件 |
| 协作工具 | 驱动其他 Agent 或请求人类协助 | 创建子 Agent、请求人工审批 |
| 用户沟通工具 | 向用户传递信息 | 回复消息、发送通知 |
| 事件触发工具 | 在外部事件发生时唤醒 Agent | 定时器、新邮件、系统告警 |

前三类由 Agent 主动调用，是本章重点。事件触发工具由 Agent 注册、外部事件触发；用户沟通工具和事件触发工具涉及异步运行，在第六章进一步讨论。

**我的理解：**感知工具解决“知道什么”，执行工具解决“做什么”，协作工具解决“谁来一起做”。

## 4.2 工具设计的通用原则

### 4.2.1 能力如何表达

工具应围绕 Agent 要完成的目标设计，而不是机械地把每个底层 API 都单独包装成工具。能力主要有两种表达方式：

- **专用工具：**有明确的名称和结构化参数，便于校验、控制权限和审计，但每增加一个工具都会占用上下文。
- **Skill + 通用执行器：**用文档说明操作流程，让 Agent 借助终端或代码解释器完成任务。覆盖范围广，也方便修改，但复杂参数更容易传错。

通常可以优先使用通用工具。涉及**精细权限、复杂参数、高频操作或平台差异**时，专用工具更合适。例如，生产数据库写入需要严格授权，适合封装成专用工具；一般的数据计算可以交给沙盒中的代码解释器。

### 4.2.2 工具描述要帮助模型做选择

好的描述不仅说明“能做什么”，还要说明**什么时候用、不能做什么**。参数最好附具体示例，返回值要写清格式；如果调用耗时较长，也应说明。Agent 经常选错工具时，应先检查描述是否存在边界不清或参数含糊的问题。

### 4.2.3 参数传递必须保真

工具不应在模型不知情时替换字符、修改输入或追加参数。否则，模型以为自己执行了操作 A，工具实际执行的却是操作 B，失败后也难以排查。如果确实需要转换参数，必须事先说明，并在工具结果中明确告知。


## 4.3 工具生态：MCP 与 Skill Hub

**MCP（Model Context Protocol）**为 Agent 连接外部工具和数据源提供统一协议。MCP 服务器提供能力，Agent 使用的客户端负责发现并调用这些能力。它主要包含三类内容：**工具**（可执行的操作）、**资源**（可读取的数据）和**提示模板**。

**Skill Hub**用于分发 Skill。一个 Skill 通常是包含 `SKILL.md` 的文件夹，文档告诉 Agent 如何借助已有工具完成任务。MCP 侧重标准化的工具接入，Skill 侧重按需阅读操作说明。

接入第三方 MCP 服务器或 Skill 时，需要注意信任边界：

- 工具描述可能夹带诱导 Agent 行动的恶意指令。
- 服务器更新或被入侵后，工具行为可能改变。
- 名称相似的工具可能让 Agent 把敏感参数交给错误的服务。
- Skill 可能包含实际运行的代码，因此还要检查代码及其依赖。

对应的做法是：审查来源和描述、控制更新、只提供所需的最小权限，并在适当的隔离环境中运行不可信能力。

**我的理解：**接入能力越方便，越要弄清“这项能力是谁提供的、它能访问什么、运行时会做什么”。



## 4.4 工具太多时：组织与发现

当工具增加到成百上千个时，把全部工具定义一次性放进上下文，会消耗大量 token，也会让 Agent 更容易选错工具。解决思路是**按需展示能力**。

1. **层次化组织：**先按用途分组，例如搜索、读取、解析和查询。Agent 先确定需要哪一类，再找具体工具。
2. **按需加载：**初始只展示工具名称或简短索引；Agent 需要使用时，再读取完整的参数和说明。
3. **主动工具发现：**任务执行过程中，如果 Agent 发现缺少某种能力，就用自然语言描述需求，由系统搜索并加载匹配的工具。这比只根据用户最初的问题预选工具更灵活。
4. **渐进式查阅 Skill：**Agent 先看 Skill 的名称和简介，需要时才读正文，再按文档指引读取脚本或补充资料。

动态加载工具时，还要尽量保持系统提示词等上下文前缀稳定，避免每增加一个工具就使已有的计算缓存失效。

**需要分清的两个决策：**“把能力做成专用工具还是 Skill”决定单项能力的表达方式；“一次展示多少项能力”决定工具库如何向模型开放。选择了 Skill，也仍然可能需要组织和检索大量 Skill。



## 4.5 感知工具：让 Agent 获取信息

感知工具的主要难点是**控制返回的信息量，同时不让 Agent 误解结果的完整性**。一次搜索可能有大量结果，一份文档也可能有上百页；全部放入上下文，会增加成本并淹没关键信息。

- **搜索工具：**先返回标题、位置和摘要等候选信息，让 Agent 决定深入读取哪一项；结果较多时提供分页。
- **读取工具：**支持指定起始位置和读取长度。必须截断时，明确说明省略了多少内容，以及如何继续读取。静默截断会让 Agent 误以为已经看完。
- **缓存与并行：**感知工具通常只读，不改变外部世界，因此相同结果适合缓存，彼此独立的读取或搜索也适合并行。

### 多模态信息的三种处理方式

| 方式 | 优点 | 局限 |
| --- | --- | --- |
| 模型直接理解图片、音频或页面 | 保留图表、布局等信息 | 通常占用更多上下文 |
| 先提取为文本 | 处理文字为主的内容较经济 | 可能丢失图像和空间关系 |
| 调用专门的多模态分析工具 | 按问题获取简短分析结果 | 效果取决于工具的分析能力 |

**选择方法：**纯文字内容可以优先提取文本；图表、复杂表格、界面和版式重要的页面，应保留视觉信息。

## 4.6 执行工具：让 Agent 改变外部世界

执行工具可以写文件、运行命令或调用外部服务。它们会产生实际后果，因此错误代价通常高于感知工具。

### 分层安全防护

1. **输入验证：**执行前检查路径、命令和参数是否合法；发现异常就明确报错，不要暗中“修正”。
2. **权限控制：**限制可访问的目录、服务和资源。危险命令清单只能作为基础防护，不能单独依赖。
3. **独立审查：**对影响重大或不可逆的操作，在执行前增加审核；无法判断时交给人处理。
4. **环境隔离：**在适当的沙盒中运行通用执行工具，并限制 CPU、内存、磁盘和网络资源。Python 虚拟环境只隔离软件包，**不等于安全沙盒**。

### 两种独立审查方式

- **提议者—审核者：**由一个模型提出行动，另一个独立视角在执行前判断是否合理，或在执行后验证结果。适合重要操作和复杂成果的检查。
- **Sidecar：**在单次工具调用真正执行前，独立检查工具名称及参数等结构化信息，判断是否安全。它审查的是具体调用，应尽量避免受到主 Agent 所读网页或其他自由文本中恶意指令的影响。

### 执行后的验证与反馈

如果操作结果可以检查，就应尽快验证，并把结果返回给 Agent。例如，写入代码后立即运行语法检查；检查失败时返回具体位置和错误信息，使 Agent 能在下一轮修正。这构成了**“执行 → 验证 → 反馈”**闭环。

执行命令可能产生很长的输出。工具可以只把开头、结尾和省略提示放入上下文，同时保存完整结果，并告诉 Agent 如何继续查看。执行记录也应包含调用时间、参数、结果和耗时，便于排查问题。

### 超时与重试

**调用超时不代表操作没有发生。**例如，创建订单的请求虽然超时，订单仍可能已经创建；直接重试可能产生第二笔订单。

可采用两种办法降低重复执行的风险：

- 给操作附上唯一标识，由服务端识别并拒绝重复请求。
- 重试前先查询当前状态，确认操作确实没有完成。

邮件、转账等会产生真实世界后果的操作，尤其不能盲目重试。应先检查目标和待执行内容；若执行结果不确定，先核实状态，再决定下一步。

**我的理解：**执行工具返回“成功”还不够，Agent 需要知道结果是否正确；返回“超时”也不够，Agent 需要知道操作是否已经生效。

## 4.7 协作工具：与其他 Agent 和人配合

当任务适合分工，或需要特定能力与人工判断时，Agent 可以通过协作工具委托子任务、交换消息并汇总结果。

### 子 Agent 的任务要交代清楚

给子 Agent 的任务应明确四件事：**负责什么、可使用哪些上下文、职责到哪里为止、按什么格式返回结果**。尤其要区分主 Agent 的指令、用户的补充信息和工具返回的数据，避免把不同来源的内容混为一谈。

常见的协作操作包括创建子 Agent、发送补充消息、查看运行状态和结果，以及在任务不再需要时取消它。协作可以是等待结果的同步方式，也可以是先取得任务 ID、完成后再取回结果的异步方式。

### 人工介入

有些关键判断需要人的专业知识、偏好或批准。请求人工协助时，应说明需要判断的事项，并设置等待超时后的处理方式。人的批准、拒绝及其理由也可以成为反馈，帮助后续改进 Agent 的规则、知识或能力。

**我的理解：**协作的关键不只是“多找一个 Agent”，而是让每位参与者都清楚任务边界，并让结果能够可靠地交接。


## 4.8 本章小结

工具设计决定 Agent 能接触哪些信息、能够采取哪些行动。设计工具时，我认为最重要的是以下四点：

1. **先选能力的表达方式：**通用工具和 Skill 覆盖面广；需要精细权限、复杂参数或稳定接口时，使用专用工具。
2. **再决定如何展示能力：**工具多时采用分类、索引和按需加载，减少上下文开销与选择错误。
3. **按工具的后果设计接口：**感知工具要控制信息量并标明截断；执行工具要控制权限、验证结果并谨慎重试；协作工具要明确任务边界和交接方式。
4. **始终关注信任边界：**第三方工具描述、返回内容和 Skill 都不能因为“看起来像说明文档”就被直接当作可信指令。

**一句话总结：**好的工具系统既要让 Agent 找得到、用得对，也要让它知道操作是否成功，以及哪些事情不能自行决定。
