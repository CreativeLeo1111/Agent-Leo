# 第五章重点梳理：Coding Agent 与通用 Agent


## 一句话抓住本章

对**开放任务型通用 Agent**而言，Coding Agent 加文件系统构成能力底座：模型理解目标并生成代码，文件系统承载记忆、数据、工具和产物，Harness 提供约束、验证、纠错与回退。代码之所以重要，是因为它能在运行时创造新工具、新规则和新界面，是一种“创造能力的能力”。这一架构不宜直接套到任务空间封闭的垂直客服等场景。（120–122、134、149 页）

## 1. 为什么 Coding 是通用 Agent 的底座

开放任务的类型和产物无法预先穷举。代码可把自然语言需求转成可执行步骤，处理计算、数据、文档、接口和自动化；文件系统则让这些步骤的输入、输出和经验持续存在。书中的 OpenClaw 案例用 Markdown 文件保存长期记忆，用脚本处理数据，再把报告、图表和新经验写回文件。（120–122 页）

基础能力可以概括为：**找文件 → 读内容 → 写或编辑文件 → 执行命令与代码 → 检查结果**。书中为便于说明列出代码解释器、终端、读文件、写文件、编辑文件、文件名搜索、内容搜索七类工具；这不是必须照搬的固定数量，一个功能充分的终端也能承担其中多项操作。（120–121 页）

## 2. 从“会写代码”到“能交付”：完整工作闭环

```text
理解项目与约定
    ↓
澄清目标、边界和验收标准
    ↓
复杂任务先形成设计
    ↓
实现并运行测试
    ↓
根据错误修复，审查代码与安全性
    ↓
同步文档，交付可验证的结果
```

这个流程按任务复杂度裁剪：简单修复可以直接实现；需求模糊、影响范围广时，需要先调查和设计。关键完成标准是**结果通过验证**，而非“代码已经写完”。项目文档和 Agent 指令文件让架构、测试方法、约束和禁区可见，减少 Agent 对隐含知识的猜测。（123–124 页）

## 3. Harness 让能力可控、可恢复

本章把 Harness 落到四类工程设施：**验收基线**（测试、CI、审查标准）、**执行边界**（权限、模块和依赖约束）、**反馈信号**（类型检查、lint、测试错误）与**回退手段**（Git、沙盒、快照）。目标明确且结果可自动验证的任务最适合 Agent；目标模糊时，自动化甚至会让它更快跑偏。（125–126 页）

可靠性来自一条完整的恢复链，而非盲目重试：

1. **识别故障**：区分 API、工具、上下文和控制流问题；用重复调用指纹、连续失败计数、流式输出看门狗发现无进展或静默卡死。
2. **选择恢复动作**：暂时性故障退避重试；参数、权限等确定性错误要修改输入或策略；将结构化错误反馈给模型。必要时降级或换模型接续，但历史轨迹应保存为可移植的中立格式。
3. **及时熔断**：每条恢复路径设置次数上限，并有全局轮数、预算和人工介入条件，避免修复逻辑自身引发循环。（126–128 页）

效率方面，独立工具调用可并行，完整生成并校验的调用可提前执行；大型文件按行读取，长输出截断并保留原文；工作目录、分支和变更等动态状态及时注入上下文；编辑后立即返回语法检查结果。（128–130 页）

## 4. 搜索、编辑与安全是基础设施中的关键细节

- **搜索**：`glob` 找路径，`grep` 找准确文本；语义搜索帮助发现用词不同但功能相近的代码，符号搜索追踪定义和引用。具体组合取决于代码库和工具成本，不必为语义搜索一律建索引。（130–131 页）
- **编辑**：旧字符串替换可预测，但要求原文匹配且唯一；行号定位便于大段修改，却容易受前次编辑影响；首尾字符串定位试图兼顾简洁和稳定。选择标准是定位是否明确、失败是否可检测。（131–132 页）
- **安全**：当 Agent 同时接触私有数据、不可信内容和外部通信时，提示注入可能形成数据外泄路径；持久记忆还可能把攻击跨会话保存。防线包括限制沙盒的网络出口、文件和资源访问，按命令实际效果审查危险操作，并把第三方内容当作数据而非有权发令的指令。（132–134 页）

## 5. 代码作为“元能力”：从内部推理扩展到外部世界

本章的六种用途可以按作用对象从内向外理解：（134–149 页）

| 作用对象 | 代码承担的角色 | 关键判断或约束 |
| --- | --- | --- |
| 思维 | 把计算、符号推导、逻辑条件交给求解器执行 | 模型负责理解和形式化；代码结果仍取决于建模是否正确。 |
| 业务规则 | 把政策变成确定性的校验与执行逻辑 | 自然语言规则用于解释；关键操作由服务端依据数据库真值和服务端时钟最终裁决。 |
| 内容呈现 | 程序化生成 PPT、视频和精确几何体 | 先生成再渲染，由独立审核者根据实际效果反馈；精密、可参数化的产物尤其适合代码。 |
| 系统接口 | 临时编写适配器、解析器和诊断脚本 | 适应接口或日志格式变化时，应经测试，避免把真实故障误当成正常变化。 |
| 用户界面 | 生成表单、图表、查询和可定制应用 | 标准交互宜用受信任组件渲染声明式描述；生成的 SQL 与代码须受权限和沙盒约束。 |
| Agent 自身 | 修复运行环境，基于成熟范例生成新 Agent | 常见故障先用确定性检查；新 Agent 继承经过验证的架构并测试，避免从零复制错误。 |

其中，**提议者—审核者**贯穿 PPT、视频和日志可视化：生成者写代码，审核者查看渲染后的真实产物，返回结构化问题，迭代到质量达标或预算耗尽。审核者能看到生成者仅靠代码无法确认的效果。（138–140 页）

生成式 UI 还有一条重要的数据路径：Agent 可生成 SQL 或可视化程序作为产物，让数据库结果直接进入界面，省去模型复述大表格的成本和抄写错误。但查询只能在受控、只读、限时、限量的权限下运行。若应用层代码可以动态重写，最终的数据权限必须由稳定的数据层强制执行，并使用可信运行时绑定的身份，防止新代码绕过校验。（145–147 页）

## 贯穿全章的结论

**通用性**来自代码可以临时扩展能力；**持续性**来自文件系统保存记忆、产物与经验；**可靠性**来自可执行约束、自动验证、故障恢复和回退；**安全性**来自把关键权限与事实校验放在模型和动态代码都不能自行改写的边界上。四者合在一起，Coding Agent 才从“能生成代码的模型”成为“能完成开放任务的系统”。（120、125–128、134、147–149 页）
