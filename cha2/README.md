# Agent 第二章学习

本章的目的是上下文内容的详细学习

## 上下文是决定agent能力的关键

上下文用来分析出用户的查询，后续结果回答的好坏完全有接收到的信息正确以及效率相关。

上下文有五个组件：
1、系统提示词：它由开发人员编写，用来定义整个结构的角色、遵守的规则。相当于新人刚进入公司要遵守的员工守则。
2、工具定义：定义一些需要使用的特定功能的函数，并能够对其调用。
3、对话历史：以往历史对话或者调用函数后的结果。
4、本论的思考：包括对历史以及工具结果来判断是否可以用来输出结果，如果还没达到要求就需要使用其他工具继续进行。
5、生成的词语位置：顺序会导致实际含义发生改变。

当然模型的回答的过程并不仅仅是这些，它需要借助ReAct循环，判断工具调用是否合理以及结果是否达到输出的程度。

一个Agent就像一个新员工，需要给足背景信息，它才能干得很好。Agent也像人一样，如果有一个比较好的工作流程给它，它一步一步做，最终能够实现任务。那怎么样能够让它遵守自己的员工守则以及岗位职责去做呢？这就涉及到下面所说的API的调用了！

## API的调用

### 系统提示词
由开发者编写，有最高优先级。用于定义整体的功能（比如定义聊天机器人）

### 用户消息
用户输入的信息，用于查到想要的结果。

### 助手消息
记录模型之前的回复，将工具调用的结果记录下来。让模型记住自己说过的话。

### 工具结果
将得到的结果以tool角色返回个模型，并且和调用的工具指令一一对应。

## 关于ReAct循环的一些理解
我认为，首先由大模型想出能解决用户的路线，并且结合系统提示词，给出工具调用的命令（给定命令不返回结果），然后由工具接受命令去实现一系列功能，再将工具结果回馈给助手，模型判断是否还需下达命令，如果不用，则输出结果。若结果不足以输出，则继续下达指令，直到完成用户任务。

关于这个会在本地LLM服务实验中展示详细。

## Agent的上下文管理
静态前缀+动态前缀

静态前缀往往是系统提示次+工具定义那些内容

动态前缀往往加入的是会话中得到的工具结果、历史消息等内容，记录的是agent解决问题的行动轨迹。

有个特别值得关注的问题，静态前缀不要改，哪怕是一个字符，因为后面的ReAct循环会一直使用。后续要加入的用户信息添加再动态轨迹（前缀）中。
