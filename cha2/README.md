# Agent 第二章学习

本章的目的是上下文内容的详细学习

## 2.1 上下文是决定agent能力的关键

上下文用来分析出用户的查询，后续结果回答的好坏完全有接收到的信息正确以及效率相关。

上下文有五个组件：
1、系统提示词：它由开发人员编写，用来定义整个结构的角色、遵守的规则。相当于新人刚进入公司要遵守的员工守则。
2、工具定义：定义一些需要使用的特定功能的函数，并能够对其调用。
3、对话历史：以往历史对话或者调用函数后的结果。
4、本论的思考：包括对历史以及工具结果来判断是否可以用来输出结果，如果还没达到要求就需要使用其他工具继续进行。
5、生成的词语位置：顺序会导致实际含义发生改变。

当然模型的回答的过程并不仅仅是这些，它需要借助ReAct循环，判断工具调用是否合理以及结果是否达到输出的程度。

一个Agent就像一个新员工，需要给足背景信息，它才能干得很好。Agent也像人一样，如果有一个比较好的工作流程给它，它一步一步做，最终能够实现任务。那怎么样能够让它遵守自己的员工守则以及岗位职责去做呢？这就涉及到下面所说的API的调用了！

## 2.2 API的调用

### 系统提示词
由开发者编写，有最高优先级。用于定义整体的功能（比如定义聊天机器人）

### 用户消息
用户输入的信息，用于查到想要的结果。

### 助手消息
记录模型之前的回复，将工具调用的结果记录下来。让模型记住自己说过的话。

### 工具结果
将得到的结果以tool角色返回个模型，并且和调用的工具指令一一对应。

## 关于ReAct循环的一些理解
我认为，首先由大模型想出能解决用户的路线，并且结合系统提示词，给出工具调用的命令（给定命令不返回结果），然后由工具接受命令去实现一系列功能，再将工具结果回馈给助手，模型判断是否还需下达命令，如果不用，则输出结果。若结果不足以输出，则继续下达指令，直到完成用户任务。

关于这个会在本地LLM服务实验中展示详细。

## 2.3 Agent的上下文管理
静态前缀+动态前缀

静态前缀往往是系统提示次+工具定义那些内容

动态前缀往往加入的是会话中得到的工具结果、历史消息等内容，记录的是agent解决问题的行动轨迹。

有个特别值得关注的问题，静态前缀不要改，哪怕是一个字符，因为后面的ReAct循环会一直使用。后续要加入的用户信息添加再动态轨迹（前缀）中。

## 2.4 KV Cache机制

输入的token以注意力极致的方式计算每个token的Q、K、V值，根据value值来连接token，预测下个词。然而在token有很多的时候，每次计算Q、K、V值非常耗内存，那就想到能不能有一种机制能处理这个情况。

KV Cache机制就是这样的作用，它计算每个token的Q、K、V然后记录起来，后续需要使用某一个token的值时，拿出来调用即可，不必每轮都计算一遍。

API的消息格式是JSON文件，不方便明显识别每个token的角色，那就引入了Chat Template。它把系统、用户等的内容信息分隔开了，<user> ,<system>之内的，能清晰明了知道各个角色的分工。KV Cache以同样的方式存储计算的token结果，只有遇到新的token时才会计算并存储。这也就是说，当用户问“今天天气怎么样？”，KV Cache机制会计算token的结果，并在后续用户仍提问类似问题时调用已计算的结果。如果改变了问题比如问：“北京有什么好玩的地方？”，那么KV机制就得在修改后的节点token计算，和之前已经算好的不能匹配。

需要注意的是KV Cache同样需要规范前缀，随着迭代次数增加，注意力计算呈平方级增长。

## 2.5 提示词工程
这一部分，用来优化系统提示词，让大模型更容易找到自己的身份，以及自己的岗位守则。

这就说明，开发人员可以根据任务的分工不同，对不同的agent给不同的风格。以及给定结构化框架，让agent完成任务的效率更高。结构化的框架，我理解的意思是，一份更细致的员工守则，在哪个阶段就完成哪个阶段的任务，一个个任务完成了，最后也就完成了目标。很像是对目标的拆解。写清楚结构化框架很重要，不要让任务重复和理不清楚。

### 流程驱动
让agent知道自己处于哪个阶段，当前目标是哪个。

### 规则堆砌
就是把员工守则说的更明白，但是做任务的流程等等还没说清楚。

### 工具定义
与系统提示词一起写到静态前缀前面，让agent一开始就明白，工具的适用性和边界。

### 上下文安全
防御的核心是，将来源的输入标注清楚，哪些是外部环境所给的，哪些是系统助手给的分析结果，以及工具结果等等


## 2.6  动态提示词与agent skills
skill有按需加载的特点，agent需要知道该用它的时候。skill就是给了一份更专业的岗位守则，针对特定的任务，有高效的处理方式，并且仍然有好的输出结果。

## 2.7 agent状态栏
状态栏，顾名思义就是用来区分不同状态的，这里用来区分回答内容所归属的地方。让用户接受信息等更高效，也更容易判断agent内容的有效性等。
